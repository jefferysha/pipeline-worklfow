AFK 首跑引导 — loop 的字段该由谁来填?

用户原话:「这些让用户填，体验太差，怎么可能填得出来。」确实，15 个 loop 字段里近半数只是给 readiness 评分看的「作文」，真正卡执行的字段没几个。三个方案给出三种「谁来当生产者」的分工，四件套(就绪三灯/首跑旅程/镜像下拉/凭证面)与关系图三方案共有，写法各有取舍。点开每张卡试试，选一个，回复方案字母即可。

谁来填这些字段 — 生产者图例数据来自 loop 卡 15 个字段的运行时消费审计(maps/loopafk.md §1)
agent 生成 agent 在终端对话里已经知道目标语境，直接起草：goal / design_doc / kill_criteria 这类容易被人敷衍的「作文」字段。
系统推导 从别的已知值算出来，不需要人凭空想：change_prefix←id、state←约定路径、kill_criteria 预设←风险档。
人拍板 真正牵涉利害、必须人决定的开关：status 启停、autonomy_level 自主级别，以及要不要批准这份草稿。
status● 硬消费kill-switch：enforce R1 直接读它，paused/retired 判定必须遵守
change_prefix● 硬消费在途计数 / denylist 归属 / runner 归属，三处运行时真读
runner● 硬消费codex 分流 + 凭证白名单透传就靠这个字段判断
kill_criteria◐ 软消费只计 readiness 20 分，判据本体是 enforce 硬编码 R1-R11，字符串不解析
phases○ 零消费全仓无任何运行时消费者，纯声明标签
allowlist○ 零消费「执行面另落」，本轮无消费者，写了也不生效
A终端生成，UI 审阅 主推 · loop 空态不再给表单，agent 在终端写草稿，UI 只做批准/调整/驳回

配置由 agent 在终端写草稿，UI 只负责审阅：批准、调整或驳回，不再让人对着空表单编故事。
