# /goal — 定义本轮目标

在开始一轮新的自主/agentic 工作（新起一个终态，或在已有终态内开新的一大轮）之前，先把
「做完算什么」钉死，再动手写实现代码。这不是新发明的纪律——`GOAL.md` 已经用 v1.0/v2.0
两轮终态 + 清单 A-F 证明过这套纪律有效（证据先于勾选、清单只增不删、勾选需要测试名/
commit/oracle 报告）。本命令把「怎么产出下一个终态条目」的步骤仪式化，避免临时起意的
新一轮工作绕开这套已经验证过的流程。

## 实现真相源

- 真相源不是某个 CLI 子命令，而是仓库根 **`GOAL.md` 本身**——它已经是本仓「目标账本」的
  既有事实源（两轮「终态」+ 清单 A-F，代码里大量 `GOAL B18`、`GOAL A4 M4` 式注释都指回
  这个文件）。本命令**不新造一个平行的目标存储**，只是把「怎么写出下一个终态条目」的
  步骤定下来。
- 方案文档（架构提案、三方 review 结论等）是**输入**，`GOAL.md` 追加的清单条目是**拍板后
  的输出**——两者不是一回事：输入可以被否决、修正、部分采纳；`GOAL.md` 一旦有条目就要求
  证据、不倒退、不能因为「方案改了」就静默删掉已勾的项。

## 输入

- 新一轮工作的粗粒度意图：一句话诉求 / 交接文档路径 / 已有方案文档路径
- 若已有独立第三方评审（如 codex review）结论，作为**待确认输入**提供，不当既定事实——
  即便评审很详细、很有说服力，也可能存在被误判、被过度采纳或方案之间互相矛盾的地方

## 执行步骤

1. **读现状**：读 `GOAL.md` 最新一轮「终态 vX.0」章节，弄清哪些已收官、本轮真正新增的
   范围是什么；读输入方案/交接文档，标出哪些结论已经过独立事实核验（真读代码/真跑命令
   verify 过 file:line 级别的引用）、哪些只是转述或未被验证。
2. **起草候选**：把输入拆成三类——
   - **确定项**：已经过核验、且方案内部不冲突，可以直接写进候选清单
   - **待拍板项**：存在真实分歧、激进选项、或方案未覆盖的决策点（通常 ≤4 个，多了说明
     方案本身还不成熟，不该急着拍板）
   - **非目标**：方案明确排除的范围，以及排除的理由
3. **AskUserQuestion 拍板**：只对「待拍板项」发问，每题给出选项与取舍（推荐项排第一并
   标注理由）；不逐条重问已经独立核验过的结论——那是在制造对齐表演，不是真的在决策。
4. **落笔 `GOAL.md`**：追加新的「终态 vX.0」+ 清单区块，沿用既有格式——checkbox 全部
   起始未勾选、写明「达成判定」一行、非目标单独成段不与清单混排、**只增不删**。
5. **不写码**：本命令的产出到 `GOAL.md` 编辑为止。进入实现是下一个独立步骤（通常先运行本插件
   打包的 `writing-plans`，再按 pipeline 的 spec → build 流程执行），需要用户在这之后再次确认才开始——
   拍板 goal 不等于拍板「现在就开始写」。

## 诚实约束（不可阉割）

- **清单条目勾选前必须有证据**（测试名 / commit hash / oracle 报告），不许「应该能过」
  就先勾、不许为了让清单好看而提前勾选。
- **待拍板项不能替用户拍板**：独立评审的结论是输入，不是既定事实；方案之间的真实分歧
  必须原样呈现选项，不能因为自己有偏好就替用户合并成一个选项。
- **非目标要写明「为什么排除」**，不是一个空列表或者一句「以后再说」——排除理由本身
  就是防止下一轮又把同一个问题重新问一遍。
