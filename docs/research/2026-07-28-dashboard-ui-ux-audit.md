# Dashboard UI/UX 全量审计

日期：2026-07-28

Change：`dashboard-ui-ux-overhaul`
基线：`origin/main@2d103e330f847e003ff5909097d892f5722cca04`

## 1. 用户结果与边界

目标不是换一套装饰，而是让单人开发者在 30 秒内完成三件事：

1. 判断哪个项目、Change 或自动任务需要自己处理；
2. 看清当前状态、原因和下一步；
3. 在桌面和窄屏上都能稳定完成导航、筛选、配置和恢复。

本轮保持 Tenon 工作流语义、服务端规则和 API 契约不变。视觉和交互应落在
`packages/dashboard-app` 的 token、共享 UI、应用外壳及功能域视图内，不引入第二套 UI 库，
不使用第三方 logo、emoji 图标、渐变或霓虹光晕。

### 2.2 可确认的问题

| 维度 | 证据 | 影响 |
| --- | --- | --- |
| 移动导航 | 720px 以下仍保留 56px 左侧纯图标 rail，并隐藏全部标签 | 持续占用窄屏宽度，入口依赖记忆，设置入口远离拇指热区 |
| 移动进度 | 390px 下项目名逐词断行，横向阶段画布被压进约 320px 内容列 | 主状态和下一步难扫描，桌面画布的降级方式不成立 |
| 桌面密度 | 项目页单行卡片后存在大面积空白，内容与导航的视觉重心偏左 | 1440px 下空间利用率低，重要状态缺少聚合层级 |
| 色彩语义 | `--color-primary` 与 `--btn-bg` 映射到 green，同时还存在 blue accent | “可点击”和“成功”含义混在一起，状态色无法保持唯一语义 |
| 主题维护 | light/dark token 在系统跟随与显式主题中重复三份 | 颜色调整易漂移，评审难证明三套值同步 |
| 图标一致性 | 主导航和多数新页面用 Lucide，`shared/Icon.tsx` 仍维护 14 个手写 path | 线宽、网格和视觉重心不一致，形成第二套图标系统 |
| 页面层级 | Projects/Progress/AFK 使用 30px 标题，Machine 使用 24px，Workbench 缺全局页面标题 | 切换一级页面时定位线索不稳定 |
| 动效语言 | 共享 motion 已有 150–250ms ease-out 规范，但功能域仍有独立 GSAP 编排和弹性缓动 | 相同状态变化的节奏不一致，动效难统一验证 |
| 可访问性 | 已有语义 role、focus-visible 和 reduced-motion 基础，但移动导航标签仅视觉隐藏 | 无障碍名称存在，视觉可发现性和触控上下文仍不足 |
| 国际化 | 全局 i18n 已建立，但 AFK 与部分 Workbench 可见文案仍直接写中文 | 英文模式下出现混合语言，影响一致性和测试覆盖 |

## 3. 既有设计资料的冲突裁决

仓库存在两套时间不同的方向：

- 2026-07-09 的 `dashboard-redesign-design.md` 使用“工票车间”隐喻，并明确不做移动端专门布局；
- 2026-07-14 的 `v10-design-spec.md` 将产品定义为“玻璃驾驶舱”，明确否决工票/车间视觉，
  要求正文至少 14px、对比度至少 4.5:1，并保留状态语义色。

后者更晚，且与当前用户明确要求的完整 UI/UX、响应式和可访问性更一致。本 Change 采用后者，
并把移动端从“降级可见”提升为独立的信息重排契约。

## 4. 方案比较

| 方案 | 做法 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A. 逐页换肤 | 保留所有结构，只替换颜色、圆角和阴影 | 快，回归面小 | 无法解决移动 rail、页面层级与进度画布问题 |
| B. 统一系统 + 关键流重排 | 建立语义 token、统一图标/标题/动效；重做移动外壳和 Progress 响应式 | 同时改善一致性与关键任务效率，可分批验证 | 需要更新跨页测试，并严格控制共享层回归 |
| C. 全应用 IA 重写 | 重新设计导航和每个功能域的信息架构 | 理论上最自由 | 范围不可控，容易改动业务语义，难在单一 PR 中审查 |

采用方案 B。它不是折中式换皮：全局设计系统覆盖所有页面，结构重排集中在证据最强的外壳、
Progress 和一级页面框架；功能域内部保留已验证的数据和业务行为。

## 5. 推荐视觉方向：Calm Technical Cockpit

视觉母题来自产品真实内容：一个长期运行、需要快速扫视和偶尔介入的本地技术控制台。

- 中性冷灰画布承载长时间阅读，卡片靠边界和轻微层次区分，不靠装饰性阴影。
- cobalt/indigo 只表示当前选择、主要动作和键盘焦点。
- green 只表示成功/健康；amber 只表示等待/注意；red 只表示失败、危险和必须处理。
- purple 仅保留给编排/治理等已存在的专属域，不充当通用强调色。
- 正文保持 14px 基线；页面标题统一 30px，一级分区标题 18–20px，说明文字 13–14px。
- Lucide 作为唯一图标形状源；共享 `Icon` 保留稳定 API，但内部映射到 Lucide，避免一次性改动
  所有调用方。
- 圆角、边界、焦点环、触控目标和状态徽标由共享 token 约束。

## 6. 响应式与信息架构

### 6.1 桌面（> 720px）

- 保留紧凑左 rail，但增强选中态、标签对比与品牌识别。
- 内容区使用统一 `PageHeader` 和可读最大宽度；数据画布可按功能需要突破宽度。
- 设置弹层继续锚定 rail，连接状态在弹层内可读。

### 6.2 窄屏（≤ 720px）

- 左 rail 转为底部导航，五个一级入口保留图标与短标签。
- 品牌入口并入移动页面顶部，设置作为底栏独立按钮或安全弹层入口。
- App 主内容增加底部安全区和导航高度，不让 toast、抽屉或页面内容被遮挡。
- Progress 的状态筛选允许横向滚动，但项目/Change 卡采用纵向摘要；阶段轨独立横向滚动，
  不把整个桌面画布缩窄。
- 最小触控目标 44×44px，重要按钮不只靠颜色表达状态。

## 7. 动效与反馈

- 统一时长：即时反馈 120–160ms，组件切换 180–220ms，抽屉/大型面板 220–280ms。
- 统一缓动：`power2.out`/`power3.out`，禁止 bounce、back 和无状态含义的循环动画。
- 列表首次进入只做 4–6px 位移与淡入；状态变化优先局部高亮，不整页重播。
- `prefers-reduced-motion: reduce` 下直接呈现终态，保留可见状态差异。
- 加载、空态、错误态、离线和成功 toast 使用统一的图标、标题、说明与可恢复动作结构。

## 8. 可访问性验收

- 明暗主题的正文、次级文字、按钮和状态徽标满足 WCAG AA；正文目标 ≥4.5:1。
- 所有图标按钮具有可见文本或稳定的无障碍名称；移动一级导航显示文字标签。
- 键盘可到达所有导航、筛选、对话框和主要动作，focus ring 不被裁切。
- 200% 缩放与 390px 视口不产生文档级横向溢出；长项目名和 Change 名可合理截断或换行。
- 主题、语言、连接状态与 reduced-motion 均进入真实浏览器验收矩阵。

## 9. Red-team 问答

| 假设挑战 | 证据与结论 | 失败时的保护 |
| --- | --- | --- |
| 用户真的需要移动端吗？ | 当前请求明确包含全部 UI/UX；390px 实测暴露结构性问题 | 将移动端列为验收契约，不以桌面截图替代 |
| 全局改色会不会破坏状态识别？ | 当前 primary=green 已在混淆动作和成功 | 先建立语义 token，再迁移组件；浏览器逐主题核对 |
| 替换图标会不会破坏测试和布局？ | 共享 Icon 有稳定 name/size API，可内部映射 Lucide | 保持 API 和 `aria-hidden`，更新只依赖实现细节的测试 |
| 移动底栏会不会遮住内容？ | App 当前没有移动导航安全区 | 使用固定高度 + `env(safe-area-inset-bottom)`，主区同步 padding |
| 动效是否值得扩大范围？ | 共享 motion 已存在，问题是参数和消费不一致 | 只统一状态表达，不新增纯装饰动画 |
| 是否需要改 server？ | 所有发现都可在现有 snapshot/API 上解决 | 明确非目标，若实现发现契约缺口必须回退 Spec |

## 10. Explore 出口

Explore 已可回答最初问题：覆盖面、关键不一致、共享系统边界和浏览器矩阵均已明确。进入 Spec
时应把方案 B 拆成可验收需求，优先顺序为：

1. 语义 token 与共享视觉原语；
2. 桌面 rail / 移动底栏与 App 安全区；
3. 一级页面标题和信息层级；
4. Progress 响应式重排；
5. 图标、反馈、i18n 与动效统一；
6. 明暗主题、键盘、reduced-motion 和多视口回归。
