# Issue #44 Skill provenance implementation plan

## Delivery contract

Implement one strict, machine-verifiable source for all distributed Skill provenance without creating another worktree, changing plugin version metadata, publishing a release, modifying installed plugins, or touching unrelated Wave 0 contracts. Implementation is owned by one `luna_worker`; the root coordinator freezes this plan, reviews the resulting diff, owns the at-most-two code-review attempts, runs the single full final gate, and performs commit/push/PR delivery.

The implementation must preserve the generic legacy/custom Skill source projection where existing tests require it, while switching all canonical distribution paths to the strict v3 provenance model. No product path may trust hashes generated by a different production algorithm: filesystem validation and bundle resolution reuse `buildCanonicalManifest()`.

## Root verification and delivery (not delegated review work)

The root coordinator will inspect every changed source/generated/document file, map the diff back to all issue Acceptance/Measurement rows, and use at most two aggregate code-review attempts. Only confirmed findings return to Build. After implementation stabilizes, root runs exactly one full final gate covering targeted Vitest, complete `npm test` with bounded workers, build, hooks, bundle, architecture, dependency/release freshness, docs/OpenSpec checks and any necessary install/rollback E2E. Genuine environment-dependent skips are reported separately.

On PASS, root applies the OpenSpec delta, completes Ship/Archive evidence, fetches and validates latest `origin/main` ancestry, commits, pushes `codex/issue-44-skill-provenance`, opens a PR with `Closes #44`, and waits for exact-head CI. It does not merge or publish.

## Prototype decision

No disposable prototype is inserted. Explore found no unresolved external protocol, database model or state-machine feasibility question: the strict registry parser, canonical hash primitive, packaged CLI, candidate verifier and rollback store already exist as testable seams. The tracer bullet in Build subphase 1 is the lower-risk reversible way to expose integration errors. This decision does not waive red-first tests or the Spec review gate.

## Rollback boundary

Before commit, revert only this Change's narrow files and regenerate controlled outputs. After a candidate is built, any provenance failure must abort before release selection; rollback remains the existing exact previous immutable payload. Never restore `skills-lock.json` as a runtime fallback, synthesize missing hashes, or mutate installed plugin caches.
