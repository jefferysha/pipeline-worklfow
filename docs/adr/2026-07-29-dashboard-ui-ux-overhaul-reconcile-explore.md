# ADR：从最新 main 逐提交整合并创建替代 Dashboard PR

## 背景

PR #10 完成了桌面 Dashboard 的语义 token、可访问状态、键盘生命周期、Solution 长页导航和 workspace 身份修复，但它基于旧 main。PR #5 与后续主线改动已经修改 App、Nav、CSS、i18n、Onboarding、SolutionView 和主规格；GitHub 因此把 #10 标记为冲突。

旧 Change 已归档，旧 Verify 绑定 `bdd818220e...`，不能覆盖任何冲突解决后的 SHA。用户明确要求继续执行，并授权 PR 有问题时创建替代 PR；同时再次明确产品只面向电脑端 Dashboard。

## 决策

1. 从最新 `origin/main` 创建新的 frontend/default/full Change 与 `codex/` 分支。
2. 保留 PR #10，直到替代 PR 已创建且可审查；之后关闭 #10 并相互链接。
3. 只移植旧 PR 的产品提交，不复制旧治理历史、归档目录、Verify 报告或生成资产。
4. 按提交顺序应用增量；无冲突文件直接吸收，冲突文件以 main 为底人工加入最小修复。
5. 保留 main 新能力和 unsupported best-effort 手机代码，但支持、设计和验收只覆盖 1024–1920px 电脑端。
6. 最终从整合源码重建所有 tracked bundle，并对新 SHA 重新完成测试、代码复核与真实浏览器验收。

## 备选方案

- 直接 rebase PR #10：拒绝。旧 Verify 会失效，而且大范围冲突容易误选整文件。
- 关闭 #10 后从头实现：拒绝。会丢失历次 Verify 中已定位并修复的生命周期边界。
- 不处理冲突、继续等待：拒绝。用户已明确要求继续，并允许替代 PR。
- 删除 main 的全部手机布局：拒绝。用户要求是不投入手机端设计与验收，不是扩大为破坏性清理。

## 后果

- 优点：主线功能不回退；旧修复有清晰来源；替代 PR 基于最新 main，可独立验证和回滚。
- 代价：需要人工整合 7 个冲突文件，并完整重跑验证矩阵。
- 风险控制：每个产品提交后运行定向测试；最终构建生成资产；替代 PR 创建前不关闭旧 PR。
